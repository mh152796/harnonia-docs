Harmonia Documentation

Welcome to the official documentation for Harmonia, a music streaming platform made of three projects: a Flutter mobile app for Android and iOS, a NestJS backend API, and a Next.js admin panel. Follow this guide to set everything up, brand it and publish it.

What is in this package:
  • Flutter-App/ — the mobile app (Android and iOS).
  • Backend/ — the NestJS + PostgreSQL API.
  • Admin-Panel/ — the Next.js admin panel.
  • Documentation/ — this guide.
Setting up for the first time? Start with the backend (section 13), then the admin panel (section 14), then come back to section 1 for the app. The app and the admin panel both need a running backend.

Feature Walkthrough

A plain-language tour of what the app does, so you can find your way around before touching any code. Nothing in this section needs programming knowledge — the technical setup starts at section 1.

First launch

  • Splash screen — your logo and tagline while the app loads its settings from the backend. If you turned on maintenance mode or a forced update in the admin panel, the listener sees that message here instead.
  • Sign in or skip — e-mail and password, Google, Facebook or Apple. Listeners can tap Skip and browse as a guest; the app asks them to sign in when they try something that needs an account, such as liking a song.
  • Music taste — after the first sign-in, listeners pick genres and artists they like. This shapes their Home feed and recommendations, and can be changed later in Settings.
  • Home — the listener lands on the Home tab.

The four main tabs

TabWhat the listener does there
HomeBanner carousel, then the sections you arrange in the admin panel: top hits, playlists, just arrived, artists, moods, genres, shorts, recently played and continue listening. Free listeners also see a banner ad.
ExploreSearch by text or voice, with trending searches and suggestions. Browse all, moods, genres and fresh picks.
PremiumPremium plans with store prices, the free trial offer, the current plan status, and Restore purchases.
LibraryPlaylists, saved albums and artists, liked songs, history and downloads, with filters, search, and a grid or list view. Listeners create their own playlists here.

Listening

  • Mini player and full player — a mini player follows the listener through the app; tapping it opens the full player with artwork, seek bar, shuffle and repeat.
  • Up next and lyrics — reorder the queue, read synced lyrics, open full-screen lyrics and share a lyric card.
  • Listening tools — sleep timer, playback speed, equalizer (Android), crossfade, volume normalisation and autoplay of similar songs.
  • Anywhere — background playback with lock-screen controls, Chromecast, Android Auto and an Android home-screen widget.
  • Offline — Premium listeners download songs and albums and play them without a connection.

Free and Premium

You decide which songs, albums and playlists are Premium. Free listeners see Premium content locked and hear ads; Premium listeners get ad-free listening, downloads and Premium-only content. Premium is sold as a subscription through Google Play Billing (see section 11).

Settings

Profile and photo, your devices (sign any device out remotely), music taste, manage subscription, playback options, audio quality, push notifications, theme (light, dark or system), language (English or Bangla), clear cache, legal pages, credits, sign out and delete account.

What you control from the admin panel

Almost everything listeners see is managed in the browser, without rebuilding the app: songs, albums, artists, playlists, shorts, home sections, banners, moods and genres, Premium plans and the Premium screen text, ads, push notifications, app version and maintenance mode, legal links, app users and staff accounts. The full list is in section 14.

Recommended first hour. Set up the backend (section 13), start the admin panel (section 14) and sign in with your admin account. Upload one artist, one song with an audio file and cover, and add it to a home section. Then point the app at your backend (section 8), connect Firebase (section 4) and run it — your song should appear on the Home screen. Once that round trip works, move on to branding and store setup.

How the Pieces Connect (Architecture)

Harmonia is three projects that talk to one backend. Only the backend talks to the database and holds secrets; the app and the admin panel never connect to PostgreSQL or R2 credentials directly.

ConnectionWhat happens
App → FirebaseThe listener signs in (email, Google, Facebook or Apple). Firebase returns an ID token.
App → BackendEvery request goes to https://your-api/api/v1/... with the Firebase ID token in Authorization: Bearer (guests send none). The backend verifies the token with the Firebase Admin SDK.
Admin panel → BackendStaff sign in with email and password; the backend returns a JWT that the panel sends on every /admin/... request. Roles: viewer, editor, super admin.
Backend → PostgreSQLAll data lives here. Only the backend connects.
Backend → R2, App → R2The admin uploads files through the backend, which stores them in R2 and makes the low/normal/high audio versions. The app streams audio and images straight from the R2 public URL (or an expiring signed URL if you enable it).
Backend → Firebase Cloud MessagingPush notifications composed in the admin panel are sent by the backend, to the broadcast topic or to registered devices.
App ↔ Google Play → BackendThe app buys a subscription with Google Play Billing and sends the purchase token to the backend, which checks it with Google. Google then reports renewals and cancellations to the backend through real-time developer notifications (Pub/Sub).
App → AdMobFree listeners see AdMob ads. The ad unit IDs come from the backend (GET /ads/config), set on the admin panel's Ads page.

4. Firebase Setup

Firebase provides sign-in and push notifications.

You must use your own Firebase project. The package ships placeholder Firebase files with values such as YOUR_ANDROID_API_KEY and your-firebase-project-id. They let the project compile, but sign-in and push notifications will not work until you replace them:
  • Flutter-App/lib/firebase_options.dart
  • Flutter-App/android/app/google-services.json
  • Flutter-App/ios/Runner/GoogleService-Info.plist
No Firebase project of ours is included, so your app never connects to our accounts. Steps 1 and 2 below replace all three files.

Step 1: Create a Firebase project

  • Open the Firebase console and click Create a project. Enter a name and accept the terms.
  • Choose whether to enable Gemini and Google Analytics (neither is needed by Harmonia), then click Create project.

Step 2: Connect the app (recommended: FlutterFire CLI)

The FlutterFire CLI registers your Android and iOS apps and writes all config files for you.

npm install -g firebase-tools
firebase login
dart pub global activate flutterfire_cli
cd Flutter-App
flutterfire configure --project=<your-firebase-project-id>

Select android and ios, and confirm the package name and bundle ID from section 3. The command updates:

  • lib/firebase_options.dart
  • android/app/google-services.json
  • ios/Runner/GoogleService-Info.plist
  • firebase.json

Manual alternative

  • In the Firebase console click Add app > Android, enter your package name, download google-services.json and place it in android/app/.
  • Click Add app > Apple, enter your bundle ID, download GoogleService-Info.plist and drag it into Runner/ in Xcode (tick "Copy items if needed").
  • Run flutterfire configure once anyway, or update the values in lib/firebase_options.dart by hand — the app reads its Firebase settings from that file.

Step 3: Enable sign-in methods

  • Open Build > Authentication > Sign-in method.
  • Enable Email/Password, and the social providers you want (configured in section 5).

Step 4: Service account for the backend

The backend verifies sign-ins and sends push notifications with a Firebase service account: Project settings > Service accounts > Generate new private key. You will paste this JSON into the backend's .env in section 13.

5. Social Sign-In and Push Notifications

The login screen shows Google, Facebook and Apple buttons on both platforms. Configure the ones you want; to hide a button, remove it from lib/feature/auth/presentation/widgets/social_media_buttons.dart.

Google

  • Enable Google in Firebase Authentication.
  • Android: add your SHA-1 and SHA-256 fingerprints in Project settings > Your apps > Android. Add the debug key, your upload key and, after publishing, the App signing key from Play Console. Get local fingerprints with cd android && ./gradlew signingReport. Download google-services.json again afterwards.
  • iOS: download GoogleService-Info.plist again (it now contains CLIENT_ID and REVERSED_CLIENT_ID). In Xcode, open Runner > Info > URL Types, add a URL type and paste the REVERSED_CLIENT_ID value as the URL scheme.

Facebook

Register your own Facebook app. Meta's Platform Policy requires every app to use its own App ID. The package contains no Facebook App ID or client token, only the placeholders YOUR_FACEBOOK_APP_ID and YOUR_FACEBOOK_CLIENT_TOKEN. Facebook sign-in stays disabled until you replace them with your own values. If you do not want Facebook sign-in, remove the button (see the top of this section).
  • Create an app at Meta for Developers and add the Facebook Login product.
  • In Firebase, enable Facebook with your Meta app ID and app secret, and copy the OAuth redirect URI that Firebase shows into the Meta app's Valid OAuth Redirect URIs.
  • Android: in android/app/src/main/res/values/strings.xml replace YOUR_FACEBOOK_APP_ID and YOUR_FACEBOOK_CLIENT_TOKEN (Meta app > Settings > Basic / Advanced). Add your package name and key hashes in the Meta app's Android settings.
  • iOS: add these to ios/Runner/Info.plist: FacebookAppID, FacebookClientToken, FacebookDisplayName, a URL scheme fb<APP_ID> under CFBundleURLTypes, and LSApplicationQueriesSchemes with fbapi and fb-messenger-share-api. See the flutter_facebook_auth iOS guide.

Apple

  • Enable Apple in Firebase Authentication.
  • iOS: in Xcode, Signing & Capabilities > + Capability > Sign in with Apple. Xcode creates Runner.entitlements for you.
  • Android uses Apple's web flow. Create a Services ID in your Apple Developer account and set it, plus your redirect URL, in lib/feature/auth/data/datasources/auth_remote_data_source.dart (clientId and redirectUri). Follow the sign_in_with_apple Android setup. If you do not need Apple sign-in on Android, hide the button there instead.

Push notifications

  • Android: works once google-services.json is in place.
  • iOS: in Xcode add the Push Notifications capability (Background Modes for audio, fetch and remote notifications are already set in Info.plist). Create an APNs key in your Apple Developer account and upload it in Firebase: Project settings > Cloud Messaging > Apple app configuration.
  • For "Everyone" campaigns the app subscribes every device to one FCM topic, and the backend sends to it. The default is harmonia. Give your deployment its own topic name and set it in both places:
    • App: broadcastTopic in lib/core/service/push_notification/push_notification_service.dart
    • Backend: FCM_BROADCAST_TOPIC in .env
    // Flutter-App/lib/core/service/push_notification/push_notification_service.dart
static const String broadcastTopic = 'mymusic';

# Backend/.env
FCM_BROADCAST_TOPIC=mymusic

Splash screen

  • The animated splash (logo, wordmark and tagline) is drawn in lib/feature/splash/presentation/splash_screen.dart.

Brand colours

The brand colours are in lib/core/theme/src/theme_extension/src/colors/semantic.dart. Flutter writes colours as 0xAARRGGBB: FF (fully opaque) followed by the normal hex code. The default brand green is #1DDA63:

// lib/core/theme/src/theme_extension/src/colors/semantic.dart
static const Color primary = Color(0xFF1DDA63);        // brand green #1DDA63
static const Color darkBackground = Color(0xFF020E28); // dark theme page #020E28
static const Color darkSurface = Color(0xFF0B1B3D);    // dark cards #0B1B3D

Example: to use orange #FF6B00 as your brand colour, change the first line to Color(0xFFFF6B00), then stop the app and run it again (hot reload does not update const colours).

  • Theme wiring that uses these colours is in lib/core/theme/theme.dart.
  • Page colours that follow light and dark mode are in lib/core/theme/palette.dart. Dark is the default theme; listeners can switch in Settings.

8. Connect the App to Your Backend

Open lib/core/network/constants/api_endpoint.dart and set your backend's public address:

static const String apiHost = 'https://your-domain.com';   // change to e.g. https://api.yourdomain.com
  • Use the origin only — no trailing slash and no /api/v1; the app adds that itself.
  • Use https in production.
  • For local testing on an emulator use http://10.0.2.2:7001 (Android emulator) or your computer's LAN IP (real device).

Privacy policy, terms, support e-mail, store links, minimum app version and maintenance mode are not in the app code. They come from the backend and are edited on the admin panel's App config page.

9. Languages

The app ships with English and Bangla. By default it follows the phone's language when it is supported, otherwise English. Listeners can choose in Settings > Appearance > Language.

  • All on-screen text is in lib/l10n/app_en.arb (the template) and lib/l10n/app_bn.arb.
  • Generated code goes to lib/l10n/gen/ (configured in l10n.yaml).

What a language file looks like

Each language is one JSON file of "key": "text" pairs. The keys are the same in every file; only the text changes. Entries starting with @ describe placeholders and exist only in the English template. Here is part of the existing English file and its Bangla counterpart:

// lib/l10n/app_en.arb  (template)
{
  "@@locale": "en",
  "appName": "Harmonia",
  "settingsTitle": "Settings",
  "settingsLanguage": "Language",
  "settingsClearCacheSubtitle": "{size} used by images and temporary files",
  "@settingsClearCacheSubtitle": {
    "placeholders": { "size": { "type": "String" } }
  }
}

// lib/l10n/app_bn.arb  (existing Bangla)
{
  "@@locale": "bn",
  "appName": "হারমোনিয়া",
  "settingsTitle": "সেটিংস",
  "settingsLanguage": "ভাষা",
  "settingsClearCacheSubtitle": "ছবি আর অস্থায়ী ফাইলে {size} জায়গা নিচ্ছে"
}

A new Spanish file lib/l10n/app_es.arb should contain the same keys, "@@locale": "es", and keep every {placeholder} exactly as in English:

// lib/l10n/app_es.arb  (new)
{
  "@@locale": "es",
  "appName": "Harmonia",
  "settingsTitle": "Ajustes",
  "settingsLanguage": "Idioma",
  "settingsClearCacheSubtitle": "{size} usados por imágenes y archivos temporales"
}

Check: flutter gen-l10n finishes without errors and lists no untranslated keys for es. Any key you leave out falls back to English.

Add a language

  • Copy app_en.arb to app_xx.arb (for example app_es.arb), set "@@locale": "xx", delete the @ description entries and translate the values.
  • Add 'xx' to supportedLanguages in lib/core/settings/app_settings_cubit.dart: 
    static const supportedLanguages = ['en', 'bn', 'es'];
  • Add the language to the options list in the language tile of lib/feature/profile/presentation/profile/pages/profile_page.dart: 
    final options = <String?, String>{null: l10n.settingsLanguageSystem, 'en': 'English', 'bn': 'বাংলা', 'es': 'Español'};
  • Run flutter gen-l10n.
  • If the language uses a new script, add a font fallback in lib/core/theme/app_fonts.dart.

Remove a language

Delete its ARB file, remove it from supportedLanguages and the language tile, then run flutter gen-l10n.

Catalogue content (song titles, playlist names and so on) is shown as entered in the admin panel.

11. Premium Subscriptions (Google Play)

Platform note: Premium is sold through Google Play Billing on Android. Apple In-App Purchase verification is not included in this version, so Premium cannot be bought on iOS; iOS listeners use the free tier. Premium can also be granted manually from the admin panel on any platform.

iOS and App Store review

Apple requires digital subscriptions sold inside an iOS app to use Apple In-App Purchase (App Review Guideline 3.1.1). Harmonia's backend verifies Google Play purchases only, so on iOS the app must not offer a way to buy Premium. Choose one approach before you submit to the App Store:

ApproachWhat to do
A. Free on iOS (recommended, no coding)
  • In the admin panel's Premium plans page, untick ios on every plan so only android is left. New plans have both ticked by default. The backend returns plans per platform (GET /premium/config?platform=ios), so iOS then gets none.
  • Do not mark the songs a reviewer will try as Premium, or make sure the review account (below) has Premium.
  • Hide the Premium tab and "Go Premium" buttons on iOS, for example with if (Platform.isIOS) around the Premium tab in lib/feature/main/presentation/widgets/bottom_nav_widget.dart.
  • Never mention prices, "subscribe on our website" or "buy on Android" in the iOS app. Apple rejects that under 3.1.1 and 3.1.3.
B. Give the reviewer PremiumCreate a review account, grant it Premium in the admin panel (App users > open the user > Grant days), and enter its email and password in App Store Connect > App Review Information. Premium granted by you is not a purchase, so this is allowed when the iOS app has no purchase buttons (approach A).
C. Add Apple In-App PurchaseDeveloper work: create subscriptions in App Store Connect, add their IDs to the plans (the database already has apple_product_id), and add App Store receipt verification and App Store Server Notifications to the backend, next to the Google Play code in Backend/src/modules/subscriptions/. The app's purchase code already supports StoreKit through the in_app_purchase package.

Suggested App Review notes for approach A and B:

Harmonia is free to use on iOS. The iOS app has no in-app purchases and no
links or references to buying anything elsewhere. Some content is
unlocked for accounts that an administrator grants access to; the demo
account below has this access so you can review every feature.
Demo account: review@your-domain.com / your-password

If App Review still asks for a purchase mechanism, reply in Resolution Center: the iOS app does not sell digital content, access is granted by the service operator, and there are no purchase calls to action in the app. Then either remove the remaining Premium wording on iOS or implement approach C.

Step 1: Create the subscription in Play Console

  • Upload a build to a testing track first (Play Console only allows products once the app has the billing permission, which Harmonia already declares).
  • Open Monetize with Play > Products > Subscriptions and create a subscription, for example product ID premium_single.
  • Add a base plan (for example monthly, auto-renewing, 1 month) and set prices.
  • Optional: add a free-trial offer (for example free-trial-7-days).
  • Add your testers under Settings > License testing so test purchases are free.

Step 2: Add the plan in the admin panel

Open Premium plans and create a plan. Fill in the platforms (android), payment provider (google_play), the product ID, base plan ID and optional offer ID — they must match Play Console exactly. Name, features, trial text, tag, colour and button text control how the plan looks in the app. The price shown to listeners always comes from Google Play.

The texts on the Premium screen (title, benefits, trial offer) are edited on the same page under Premium page settings.

Step 3: Let the backend verify purchases

The app sends every purchase to the backend, which confirms it with Google before unlocking Premium. Set up the Google Play service account and real-time notifications as described in section 13, step 7.

How Premium works

  • Mark songs, albums or playlists as Premium in the admin panel. A song inside a Premium album is Premium everywhere.
  • Free listeners see Premium items with a lock and cannot play or download them.
  • Premium listeners get ad-free listening, offline downloads and Premium content. When Premium ends, downloads are removed from the device.
  • Restore purchases on the Premium tab restores an existing subscription on a new device.

Step 6: Media storage (Cloudflare R2)

  • In Cloudflare, open R2, create a bucket and connect a custom domain (for example cdn.yourdomain.com) under the bucket's settings, or enable its public r2.dev URL.
  • Create an R2 API token with Object Read & Write on that bucket.
  • Fill in CLOUDFLARE_R2_ENDPOINT (https://<account-id>.r2.cloudflarestorage.com), CLOUDFLARE_R2_ACCESS_KEY_ID, CLOUDFLARE_R2_SECRET_ACCESS_KEY, CLOUDFLARE_R2_BUCKET, CLOUDFLARE_R2_PUBLIC_URL (your public domain) and CLOUDFLARE_R2_PREFIX (a folder such as harmonia/).

Uploads from the admin panel are stored under <prefix>image/, <prefix>audio/ and <prefix>video/. Limits: images 10 MB, audio 60 MB, video 250 MB. Stream qualities created by ffmpeg go to <prefix>audio-variants/. Without R2 the upload endpoint answers 503 "Media storage is not configured"; you can still paste links to files hosted elsewhere (https only).

Step 7: Google Play (Premium)

A. Service account (purchase verification)

  • Play Console > Setup > API access: link a Google Cloud project.
  • In Google Cloud > IAM, create a service account and download a JSON key.
  • Back in Play Console, invite the service account under Users and permissions and grant View financial data and Manage orders and subscriptions.
  • Set GOOGLE_PLAY_PACKAGE_NAME (your app's package name) and GOOGLE_PLAY_SERVICE_ACCOUNT_JSON (JSON or base64). Until this is done, purchase verification answers 503.

B. Real-time developer notifications (recommended) — tell the backend about renewals, cancellations and refunds.

  • Generate a secret: openssl rand -hex 24 and set it as GOOGLE_PLAY_RTDN_TOKEN.
  • In Google Cloud Pub/Sub, create a topic (for example play-billing) and add google-play-developer-notifications@system.gserviceaccount.com as Pub/Sub Publisher.
  • Create a push subscription on the topic with the endpoint
    https://api.yourdomain.com/api/v1/purchases/google/rtdn?token=<GOOGLE_PLAY_RTDN_TOKEN>
    (Pub/Sub cannot send custom headers, so the secret goes in the URL; the backend hides it in its logs.)
  • Optional, stronger: enable authentication on the push subscription and set GOOGLE_PLAY_RTDN_AUDIENCE to the audience you configured.
  • Play Console > Monetization setup > Real-time developer notifications: enter the full topic name and click Send test notification.

Without notifications, subscription changes are picked up when the app re-verifies and by an hourly expiry job. Refunds and revocations are always re-checked with Google before Premium is removed.

Step 8: Expiring audio links (optional)

By default, audio URLs on your R2 domain are permanent. To make them expire, deploy the included worker docs/media-signing-worker.js:

  • Cloudflare > Workers & Pages > Create, paste the file and deploy.
  • Worker Settings > Variables: add the secret MEDIA_URL_SIGNING_SECRET (a long random value) and the variable PROTECTED_PREFIXES, for example harmonia/audio/,harmonia/audio-variants/.
  • Worker Triggers > Routes: add cdn.yourdomain.com/* (your R2 public domain).
  • Set the same MEDIA_URL_SIGNING_SECRET in the backend .env (and optionally MEDIA_URL_TTL_SEC, default 43200 = 12 hours) and restart.

Images and videos stay public; protected audio needs a valid signature, which the backend adds automatically.

15. API Reference

All endpoints live under https://api.yourdomain.com/api/v1. The full, always-current reference is the Swagger UI at /api on a development server. This section covers the conventions and the most important calls.

Conventions

  • Requests and responses are JSON (uploads use multipart/form-data with a field named file).
  • Unknown fields in request bodies are removed; invalid fields return 400 with a list of messages.
  • IDs are UUIDs, except app user IDs (the Firebase UID) and Premium plan IDs (integers).
  • Rate limits: 300 requests per minute per app install and 1500 per minute per IP by default (RATE_LIMIT_PER_MIN, RATE_LIMIT_IP_PER_MIN); admin login and password changes allow 10 per minute. Over the limit you get 429.

The response envelope

Successful responses are wrapped like this:

{
  "data": { ... },          // the actual result
  "isArray": false,
  "path": "/api/v1/songs/3f2c...",
  "duration": "12ms",
  "method": "GET"
}

Some older endpoints put their own { "status", "message", "data" } object inside data; the app and admin panel handle both forms.

Errors

// 400 validation error
{ "statusCode": 400, "timestamp": "2026-01-15T10:00:00.000Z", "path": "/api/v1/songs/create",
  "message": ["thumbnail must be an https URL", "title should not be empty"], "error": "Bad Request" }

// 404
{ "statusCode": 404, "timestamp": "...", "path": "/api/v1/songs/...", "message": "Song not found", "error": "Not Found" }

// 401 when a device was signed out remotely
{ "statusCode": 401, "timestamp": "...", "path": "...", "code": "DEVICE_REVOKED",
  "message": "This device was signed out from another device" }
CodeMeaning
200 / 201 / 202 / 204Success (202 for play and search events, 204 for deletes without a body)
400Invalid input
401Missing, invalid or expired token; device signed out
403Admin role not allowed, or the app user is banned
404Not found
409Conflict, e.g. an admin with this e-mail exists, or a purchase belongs to another account
429Too many requests
500Unexpected server error ("Internal server error"; details are only in the server log)
503A required service is not configured (R2, Google Play, RTDN token)

Authentication

App users sign in with Firebase in the app. Every request sends the Firebase ID token and the install's device ID:

Authorization: Bearer <Firebase ID token>
x-device-id: <stable id per app install>

There is no separate register endpoint: the user record is created on the first authenticated request. Many read endpoints also work without a token (guest mode).

Admins log in with e-mail and password:

POST /api/v1/admin/auth/login
{ "email": "admin@yourdomain.com", "password": "your-password" }

// response (inside "data")
{ "access_token": "<JWT>", "expires_in": "24h",
  "admin": { "id": "uuid", "email": "admin@yourdomain.com", "name": "Super Admin",
             "role": "super_admin", "is_active": true, "last_login_at": "..." } }

Send the token as Authorization: Bearer <JWT> on admin requests. Other admin auth calls: GET /admin/auth/me and POST /admin/auth/change-password with { "current_password", "new_password" }.

16. Database Schema

PostgreSQL, managed with TypeORM. Tables are defined in src/modules/*/entities/*.entity.ts; production changes ship as migrations in db/migrations/ and run automatically when the server starts.

Conventions

  • Most tables share id (uuid), createdAt, updatedAt and isDeleted (soft delete).
  • App users are keyed by their Firebase UID (varchar(128)).
  • Lists such as lyrics, audio variants and plan features are stored as jsonb.
  • Search uses the pg_trgm extension, created automatically at start when the database user is allowed to; otherwise search falls back to simple matching.

General questions

QuestionAnswer
Is music included?No. The demo uses Creative Commons tracks for demonstration only. You must own or license every track you publish.
Can I sell Premium on iOS?Not in this version: Apple In-App Purchase verification is not included. iOS listeners use the free tier, and you can grant Premium manually from the admin panel.
Can I add another payment gateway?Yes, as custom development. Premium is stored in user_subscriptions, so a new provider only needs to create rows there after a verified payment.
Do I need Cloudflare R2?Yes for uploads from the admin panel. You can also paste https links to files hosted elsewhere.
Can I host the backend and admin panel on one server?Yes. Use two nginx server blocks (for example api. and admin. subdomains).
Are any files minified or obfuscated?No. All three projects ship as readable source code. Third-party libraries are installed from pubspec.yaml and package.json.

20. Upgrading to a New Version

When a new version of Harmonia is released, download it from your CodeCanyon Downloads page and read its changelog first. Your songs, users, playlists, subscriptions and settings live in your PostgreSQL database and your R2 bucket, not in the code, so updating the code does not delete them.

Before you start

  • Back up the database (see section 16, Backups): 
    pg_dump -Fc -d harmonia -f harmonia-before-upgrade.dump
  • Keep your own changes in Git, or note which files you edited, so you can carry them over.
  • Never overwrite these files with the ones from the new package; they hold your settings:
    ProjectKeep your copy of
    Backend.env
    Admin panel.env.local (or .env)
    Flutter applib/firebase_options.dart, android/app/google-services.json, ios/Runner/GoogleService-Info.plist, android/key.properties and your keystore, lib/core/network/constants/api_endpoint.dart, app icons, strings.xml, Info.plist changes, AdMob app IDs
  • Compare the new .env.example with your .env and add any new variables.

1. Backend

cd Backend
# copy the new files over your old folder, keeping your .env
npm ci
npm run build
pm2 restart harmonia-api
  • Database changes are applied automatically. In production (NODE_ENV=production) the server runs every new migration in db/migrations/ when it starts. Each migration runs once; TypeORM records it in the migrations table.
  • Migrations only add or change tables and columns. They keep your existing rows. If a release ever needs to change existing data, its changelog says so.
  • Check what ran: npm run migration:show (applied ones are marked [X]). Run pending ones by hand with npm run migration:run.
  • If something goes wrong: npm run migration:revert undoes the last migration, or restore the backup with pg_restore -d harmonia --clean harmonia-before-upgrade.dump, then go back to the old code.
  • Development databases (NODE_ENV=development) update their tables from the code automatically and need no migration step.

2. Admin panel

cd Admin-Panel
# copy the new files over your old folder, keeping .env.local
npm ci
npm run build
pm2 restart harmonia-admin

The admin panel stores nothing itself; all data comes from the backend. Upgrade the backend first.

3. Flutter app

  • Copy the new lib/, pubspec.yaml and assets/ over your project, then restore the files you customised (list above). If you use Git, commit first and review the diff.
  • Run: 
    flutter clean
flutter pub get
cd ios && pod install && cd ..
flutter run
  • Raise version: in pubspec.yaml (for example 1.0.1+2) and publish the update as in section 12. Listeners keep their downloads, likes and playlists because these are stored on the server and on their phone.
  • Old app versions keep working with the new backend unless the changelog says otherwise. To make everyone update, raise the minimum version on the admin panel's App config page.
